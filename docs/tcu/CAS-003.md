## Objective and boundary

One command runs the editorial week, import then classify then cluster, for a fixed window. The
dashboard shows a category-filtered table of clustered stories where the owner selects the
stories for the issue, and the selection is persisted with provenance.

In scope: D10 resolved; a `week run` command that records a manifest naming every child run; a
table page with category filter, search, sort and selection; an append-only issue selection
record bound to the clustering run, the incidents and their source rows; a `select:stories`
capability; the scheduling decision.

Out of scope: any generation; any change to how incidents are formed.

## Acceptance

- For a fresh week, one command and one table produce a persisted selection whose every entry
  traces to source rows.
- The selection survives a reload and a second browser session.
- An account without `select:stories` sees no selection control, and a direct request is
  refused with a fixed code.
- A second execution over the same window reproduces the same child runs and reports the
  idempotent outcome.
